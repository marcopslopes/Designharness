# Project folders

Every design project gets a folder here: `projects/<project-slug>/`. This is
what makes work resumable across sessions instead of starting from zero
every time — see `harness/ORCHESTRATOR.md` for the full intake/routing protocol
that creates and reads these. (Renamed from `tasks/` — same schema, same
rules, just the folder and the word.)

## Schema

```
projects/<project-slug>/
├── about.md        # optional — the project's front page in Design Harness: a short tour with live
│                     # screen embeds, written for whoever opens the link (falls back to brief Intent)
├── brief.md        # truth block at the top (status, assumptions, unknowns, evidence, parked), then intent, scope, sources, constraints ("Project facts" in Design Harness)
├── sources.md      # project link catalog (articles, comps, Docs) — append rows; see documentation/guides/company-sources.md
├── findings.md      # accumulated outputs from every skill run, append-only, dated
├── debt.md          # optional until first deferred advisory — project debt register (audit/critique); see harness/references/project-debt-register.md
├── decisions.md     # designer decisions + rationale, append-only, dated
├── log.md           # routing log for this project: date | request | intent | chain | why
├── handoff.md       # optional — session-handoff output for continuing in a fresh chat
├── case-study.md    # optional — case-study output: the eight-chapter story, one Source: line per chapter
├── inbox/           # optional, created on first save — raw pastes and attached files, verbatim with a
│                     # short header, never edited. Lives in projects.local/<slug>/inbox/ only (people's
│                     # words stay out of the public repo). See harness/references/project-inbox.md
├── notes/           # optional — freestanding working/reference docs that aren't a dated
│                     # findings.md entry (IA taxonomies, workshop recaps, one-pagers,
│                     # write-ups). Findings stay skill-run-only; notes/ is everything else
│                     # that would otherwise sit loose at the project root.
├── screens/         # optional — live .tsx prototype source (*Page.tsx), discovered by
│                     # src/design-harness/projectsIndex.ts. States are props on the screen
│                     # (`?status=paused` in a link), not files. Any sub-folder becomes its own sidebar group. Any Cursor Canvas explorations
│                     # for this project (*.canvas.tsx) live here too — same folder, not a separate one.
├── docs/            # optional — pages for people, shown in Design Harness: .md (with screen and diagram
│                     # embeds) and .mermaid diagrams. Sub-folders group like screens/ ones. Human
│                     # summaries only — never copies of findings.md / decisions.md / log.md,
│                     # and never a retelling of brief.md (it already shows as "Project facts").
├── artifacts/       # optional — static exports of a Design Harness prototype, split by kind:
│   ├── decks/       #   shareable HTML decks (deck-builder output, hand-built case
│   │                 #   studies) + their support images. This is what `publish-project`
│   │                 #   reads from when mirroring to public/projects/<slug>/.
│   ├── snapshots/   #   raw ui-agent static exports of prototype state — generated by
│   │                 #   `npm run export-task-prototype` (see harness/skills/ui-agent/
│   │                 #   SKILL.md step 7 and scripts/export-task-prototype.mjs), never
│   │                 #   hand-written. Working/resumability copies, not curated for
│   │                 #   sharing by default.
│   └── qa/          #   audit/critique screenshots (contrast checks, annotation
│                     #   verifies, DS-restyle comparisons) — evidence, not deliverables.
└── testing/         # optional — closes the PRD's "how will we know it worked" question.
                      # test-plan.md (what's being validated, method, success criteria),
                      # study links (e.g. Lyssna), and a dated results write-up. Owned by
                      # the `researcher` role (see harness/agents/researcher.md) — same evidence
                      # discipline as findings.md: sourced, dated, honest about sample size.
```

Copy `projects/_template/` to start a new project folder. `about.md` ships in the template as a starter — fill it in once there's something to show, or delete it. `docs/` is created on demand, for pages the brief doesn't already cover (a flow diagram, a research readout). `notes/`, `screens/`, `artifacts/`, and `testing/` are all optional and created on demand — a research-only or ideas-only project has none of them. `artifacts/` only appears once a screen has actually been built, and its three sub-folders (`decks/`/`snapshots/`/`qa/`) only appear as each kind of export actually happens — don't pre-create empty ones. None of these are mandatory like `brief.md`/`sources.md`/`findings.md`/`decisions.md`/`log.md`.

**Publishing a public URL is a separate, opt-in step — never automatic.** Everything under `projects/<slug>/artifacts/` (all three sub-folders) stays local/sandbox by default. Only `artifacts/decks/` content ever leaves that local view, and only when the designer explicitly asks to publish/deploy/share — see `harness/skills/publish-project/SKILL.md`. It gets copied into `public/projects/<slug>/`, the only public-facing mirror; nothing in `artifacts/snapshots/` or `artifacts/qa/` is meant to go there. See [`public/README.md`](../public/README.md) for that side's own schema.

**Filling in `brief.md`'s Ownership block (`Designer:`/`Squad:`/`Gallery:`) is what puts a project in Design Harness's Team Gallery (`#/gallery`)** — the gallery reads each committed `brief.md`'s Ownership and Case study lines, never `decisions.md`/`findings.md`/`log.md`, and **never** `designer-profile.local.md` (local-only — never pushed). The designer also needs a card file in `src/design-harness/gallery-designers/`, written at first eligibility (`harness/references/gallery-card-enrichment.md`) with `audit` Step 3.5 as the safety net. `npm run -s harness:context -- <slug>` says why a project isn't showing.

**Designer card trigger (committed data only):** a designer's section appears
in `#/gallery` as soon as they have **at least one** mirrored project with a
resolved `Designer:` name and `Gallery: visible`. One project is enough —
there is no "wait until a second project" threshold, no empty "no projects
yet" placeholder card (that would require reading or pushing local profile
data), and no pre-listing names from `COMPANY-SQUADS.md`.

Human guide: [`documentation/guides/team-gallery.md`](../documentation/guides/team-gallery.md).

**Validated, not production.** Everything under `projects/<slug>/` — including anything in `screens/` or `artifacts/` — is sandbox/prototype output for design exploration and stakeholder review, not production code. It proves out a flow or surface; shipping it still means an engineering team rebuilds it against the real product codebase. Don't treat a Design Harness export or an `artifacts/*.html` snapshot as ready to deploy as-is.

**Net-new projects go through `harness/skills/design-kickoff/SKILL.md` first**
(see `harness/ORCHESTRATOR.md` §2) — when that skill runs, `brief.md` is upgraded
in place from the light default template to the fuller PRD structure in
`harness/skills/design-kickoff/references/prd-template.md`, and gate approval
gets logged as a dated entry in `decisions.md`. Iterating on an existing
prototype does not require this — the light `brief.md` template is enough.

## Rules

- **Append, never overwrite.** `findings.md`, `decisions.md`, and
  `sources.md` grow over the life of a project. Don't delete or rewrite
  prior entries — a wrong turn is still useful history. (For `sources.md`,
  mark a dead link in Notes / Why rather than deleting the row.)
- **Every entry is dated.** Use `YYYY-MM-DD`.
- **`findings.md` entries name the skill that produced them** — e.g.
  `### 2026-07-06 — ui-agent` — so it's clear which skill run generated
  which output without cross-referencing `log.md`.
- **Project links go in `sources.md`.** When the designer pastes an
  article/Doc/competitor URL for *this* project, append a table row there
  (and still cite it in `findings.md` when a skill synthesises it). Primary
  Figma/Jira/Confluence for the brief stay on `brief.md` **Sources:**;
  team-wide links go in `COMPANY-SOURCES.md` (org-pack — see
  `harness/ORCHESTRATOR.md` §0a). See
  [`documentation/guides/company-sources.md`](../documentation/guides/company-sources.md).
- **Check before asking.** Before the orchestrator asks the designer
  anything, it checks this folder first — the answer may already be in
  `brief.md`, `sources.md`, or `decisions.md` from an earlier session.
- **The stage comes from the files.** The orchestrator works out where a
  project stands (kickoff, framed, modelling, building, reviewing, handoff,
  testing, closed) from which files here have real content, and says it in
  one line when you pick the project up. Nothing to fill in — see
  `harness/references/project-stage.md`.
- **This is not the only log.** Project-scoped routing decisions go in this
  folder's `log.md` as the detailed view, but every decision — including
  fallbacks that never get a project folder at all — also gets one line in
  the global `harness/logs/routing-log.md`. See `harness/ORCHESTRATOR.md` §5.

## Naming

Slug the feature/surface, not the request: `clients-list-redesign`, not
`start-working-on-clients`. Reuse the same slug across sessions so
"continue the clients list project" resolves to the right folder.

## Prototype screens (added with the `projects/` rename)

Not every prototype page in `src/design-harness/pages/` has a project folder
behind it. The live folders are `clients-list-redesign` and
`mobile-banking-dashboard`. Their screens live in `projects/<slug>/screens/`
and are picked up by `src/design-harness/projectsIndex.ts`.

The other ~17 prototype pages predate this repo's task-folder harness
entirely (built as standalone Design Harness playground demos before
`design-kickoff` existed) and have no real project history to move into.
Manufacturing a retroactive project folder for them — inventing a kickoff
that never happened — would be worse than leaving them where they are.
They stay in `src/design-harness/pages/` as shared, unowned Design Harness playground
content until/unless someone actually runs a real project against one of
them, at which point it gets a real `projects/<slug>/` folder and its
screen moves at that point, same as any other net-new project.

Design-system catalog pages (`Button*`, `Text*`, `Badge`, `Card`, `Stack`,
`Foundation*`) are a separate thing entirely — they're Design Harness's viewer
for `context/design-system/`, not project prototypes, and don't move.

## Real work stays local (`projects.local/`)

This folder ships tracked and public with just `_template/` and this
`README.md` — no real project history. Actual project folders (brief,
findings, decisions, log, sources, artifacts, notes, testing) belong in
`projects.local/<project-slug>/` instead, which is gitignored (see
`.gitignore`), same pattern as `context/org-pack.local/` and
`designer-profile.local.md`.

**Exception — `screens/` stays under `projects/<slug>/screens/` even for
real work**, because Design Harness's routing (`src/design-harness/pages/*.tsx`)
directly imports live prototype code from it via re-export shims. Code
that the running app depends on has to stay resolvable on a fresh clone;
only the surrounding project-management paperwork is local-only. So a
real project with a built screen ends up split: `projects/<slug>/screens/`
(tracked, public, reskinned to be brand-neutral) +
`projects.local/<slug>/` (gitignored — brief/findings/decisions/etc., and
`artifacts/` if any).
